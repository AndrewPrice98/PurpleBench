# Decisions

## Dependencies

- **uvicorn[standard] (>=0.30).** The ASGI server for FastAPI, used for local runs and self-hosted deployment. The Vercel demo uses the serverless entry point instead. Same choice as STIGWatch.
- **httpx (>=0.27), dev only.** Required by Starlette's `TestClient`, used by the API tests. Not installed at runtime.
- **defusedxml (>=0.7).** Windows Event XML from recorded datasets and (later) uploaded runs is untrusted. `purplebench/telemetry.py` parses it with defusedxml and `forbid_dtd=True`, so any document with a `<!DOCTYPE>` is refused and entity declarations or external references never reach the parser (defusedxml's defaults refuse entities and external references but still accept a bare DTD), instead of the standard library parser. Runtime dependency (the parser ships in the app).
- **regex (>=2024.0).** Third-party regular expression module (https://github.com/mrabarnett/mrab-regex, PyPI `regex`). Used only for Sigma `|re` matching because its `search()` takes a `timeout`, which the standard `re` module lacks; a static pattern check alone cannot catch every catastrophic pattern (for example `(\w+\s?){1,25}!`, `\w*\w*\w*\w*!`, `.*.*.*=`). Licence verified 2026-11-10 from the repository's LICENSE.txt: additions are Apache-2.0, the parts derived from CPython's `re` remain under CNRI's Python 1.6 licence (PyPI metadata: `Apache-2.0 AND CNRI-Python`), both permissive. Runtime dependency. Installed locally at 2026.9.29 (released 2026-09-29) rather than the day-old latest.
- Everything else in `backend/requirements.txt` (fastapi, pyyaml, python-multipart, pyjwt) is pinned in `backend/requirements.txt`. No other dependency is added without an entry here.

## Sources and verified facts

Verified 2026-11-10 against primary sources (GitHub API and raw files, mitre.org). Nothing is cited from memory. Where a fact could not be confirmed, that is stated.

### 1. Atomic Red Team

- Repository: https://github.com/redcanaryco/atomic-red-team (default branch `master`, checked at commit `a0e3f9bc69fed2fd711bd1f1aa87a40c33482fe6`).
- Licence: MIT, "Copyright (c) 2018 Red Canary, Inc." (https://raw.githubusercontent.com/redcanaryco/atomic-red-team/master/LICENSE.txt; GitHub reports SPDX `MIT`).
- Test location and format: `atomics/<ID>/<ID>.yaml`, for example https://raw.githubusercontent.com/redcanaryco/atomic-red-team/master/atomics/T1003.002/T1003.002.yaml. Top-level keys `attack_technique`, `display_name`, `atomic_tests[]`. Each test has `name`, `auto_generated_guid`, `description`, `supported_platforms`, `input_arguments`, `dependencies`, `executor` (`name`, `command`, `cleanup_command`, `elevation_required`).
- Only metadata is used. The web app never ships or runs the test commands.
- **ATT&CK v19 migration (important).** Atomic Red Team migrated to ATT&CK v19 IDs (commit "Attack v19 migration (#3329)", 2026-05-02). `atomics/T1562.001/` and `atomics/T1070.001/` no longer exist. Their Windows tests moved to `atomics/T1685/` (Disable or Modify Tools) and `atomics/T1685.005/` (Clear Windows Event Logs). Test GUIDs were preserved (for example "Clear Logs" is still `e6abb60e-26b8-41da-8aae-0c35174b0967`).
- **Test numbers drift; GUIDs do not.** Splunk's dataset descriptions cite test numbers such as "T1562.001-15" from the numbering at recording time (2020-2022). Current numbering differs (for T1003.001, T1136.001 and T1562.001 the numbers no longer line up). Tests were therefore matched to datasets by test name and resolved to the current `auto_generated_guid`. Never match by index.

### 2. Recorded telemetry

#### 2a. Splunk attack_data (chosen primary source)

- Repository: https://github.com/splunk/attack_data (default branch `master`, checked at commit `c8af10d015d392fca97f9eb65181e9f06bc18e40`).
- Licence: Apache-2.0 (https://raw.githubusercontent.com/splunk/attack_data/master/LICENSE; README "License" section; GitHub SPDX `Apache-2.0`). Redistribution of trimmed subsets is allowed with the licence text and notices retained (see THIRD_PARTY.md).
- Layout: `datasets/attack_techniques/<TechniqueID>/<dataset_name>/` holding a `<name>.yml` manifest (author, id, date, description, environment, `mitre_technique`, `datasets[]` with `path`, `sourcetype`, `source`) plus `.log` files. 72 technique folders have an `atomic_red_team/` dataset (counted from the git tree API; the tree response was not truncated).
- Content format: `.log` files are Windows Event Log XML, one `<Event xmlns='http://schemas.microsoft.com/win/2004/08/events/event'>...</Event>` per line (`sourcetype: XmlWinEventLog`; `source: XmlWinEventLog:Microsoft-Windows-Sysmon/Operational` or `XmlWinEventLog:Security`). Verified by reading the first bytes of `T1490/atomic_red_team/windows-sysmon.log`: Sysmon event 10, `Computer` `win-dc-770.attackrange.local`, timestamps in January 2021.
- Storage: **Git LFS.** `.gitattributes` routes `datasets/**/*.log`, `*.json`, `*.ndjson` and `*.csv` through LFS. `raw.githubusercontent.com` returns a ~130-byte pointer (`version https://git-lfs.github.com/spec/v1`, `oid sha256:...`, `size N`); the `size` line is the real file size (used in the table below).
- **Downloadable without LFS tooling: yes.** `https://media.githubusercontent.com/media/splunk/attack_data/master/<path>` serves the real content over plain HTTPS (a HEAD request returned 200 with `Content-Length` equal to the pointer's size, and an HTTP `Range` request returned the first bytes). No git-lfs install is needed, and ranged or streamed reads are possible, so the dataset build can pull and trim without cloning.
- Caveat: datasets are whole attack_range runs, typically 10-50 MB per Sysmon file (one is 85 MB). The 26 files in the table total about 477 MB, so they must be trimmed to the events in each test window plus a benign baseline to meet a ~30 MB repository budget.
- Caveat: telemetry dates from 2020-2022 and covers the technique's tests as a run, so a dataset is linked to a specific Atomic test only where the manifest description names it (column "Link" below).

#### 2b. OTRF Security-Datasets (fallback)

- Repository: https://github.com/OTRF/Security-Datasets (last push 2024-03-20).
- Licence: the `LICENSE` file is MIT ("Copyright (c) 2021 Open Threat Research Forge"; GitHub SPDX `MIT`). **Ambiguity:** the README also contains a "License: GPL-3.0" line linking to a different repository's licence. That conflict is unresolved, so OTRF data is not committed unless it is clarified.
- Format: zipped JSON event files (for example `datasets/atomic/windows/credential_access/host/cmd_lsass_memory_dumpert_syscalls.zip`, 12,915 bytes), grouped by tactic folder (collection, credential_access, defense_evasion, discovery, execution, lateral_movement, other, persistence, privilege_escalation). Smaller files, but fewer techniques and JSON rather than XML.
- Decision: **Splunk attack_data is primary** (Apache-2.0 is unambiguous, it covers all 26 selected techniques with Sysmon XML, and it supports ranged HTTPS reads). OTRF is the documented fallback for a technique whose Splunk file proves unusable.

## Recorded telemetry and the technique library

Built by `backend/scripts/build_datasets.py` from files fetched by `backend/scripts/fetch_sources.py` (both pin the commits above). Downloads go to a scratch directory outside the repository and are parsed as untrusted data (defusedxml, `yaml.safe_load`, scripts run with `python -I`).

- **Content format.** Splunk's `.log` files are not strictly one event per line: a command line containing a newline spreads one `<Event>` over several lines, and events are not sorted by time. The reader splits on `<Event ...>`/`</Event>` tags and sorts by `(ts, host, record_id)`.
- **Channels.** Only the Sysmon `windows-sysmon.log` of each recording is imported. The `windows-security.log` files next to them are Splunk's legacy `key=value` text (not XML), and spot checks show they come from different recordings (other computer names such as `EC2AMAZ-...`, other times), so mixing them into a Sysmon window would put unrelated hosts side by side. `windows-powershell.log` (4104 script blocks, about 400 MB) is also not imported, to stay inside the size budget. Consequence: committed telemetry has one channel (`Microsoft-Windows-Sysmon/Operational`). The normaliser handles Security 4688 and the others and is tested on synthetic events; real Security-channel and PowerShell script-block telemetry is a known gap. The Splunk repository has XML Security files for a few techniques (`T1021.002/windows-security-xml.log`, `T1490/4688_xml_windows_security_delete_shadow.log`) that could be added later.
- **Window derivation.** The logs carry no execution windows, so each test window is derived from the events. Process-creation events (Sysmon EID 1; Security 4688 is supported too) whose image plus command line matches the test's command (default arguments substituted) are the anchors. Anchors are grouped into per-host clusters (gap at most 120 s); the earliest cluster is used. The window is 30 s before the first anchor to 120 s after the last, all event ids, on the anchor's host only (the Splunk files merge several hosts). Windows over 15,000 events shrink their trailing then leading context (flagged); `manifest.json` records method, host, start, end, anchor counts, clusters found and flags per file. No anchor means `whole-file-head` (first 1,500 events of the busiest host), flagged in the manifest.
- **Context in a window.** Each Atomic run executed the technique's tests back to back, so a window can also contain the neighbouring test's events (for example the 120 s after `Scheduled task Local` include later schtasks tests). This is deliberate surrounding noise, so scoring is by the expected technique and does not treat other tests' hits as this test's.
- **Link labels** (manifest `link`, library `link`): `named` = the dataset description names the test and the events show it; `command-matched` = the description does not name it but a recorded command line equals the test's command; `recorded` = not tied to a named Atomic test, kept with `atomic: null` and `execution_kind: "recorded technique execution"`. Tests are matched to datasets by name/GUID, never by index.
- **Deviations from the selection table above**, all because the events decide:
  - T1059.001: "Powershell Invoke-DownloadCradle" is a manual test with no command text and cannot be recognised in events. "Run Bloodhound from Memory using Download Cradle" (`command-matched`) is used instead; its command appears in the recording.
  - T1021.002: the shipped Sysmon file holds only 10 events and has no `net use`, so "Map admin share" cannot be shown. "Copy and Execute File with PsExec" is used (named in the same description, command present).
  - Upgraded from dataset-level to `command-matched` where the recorded command equals the Atomic command: T1569.002, T1548.002, T1082, T1069.001, T1105.
  - T1558.003 (no kerberoasting in the file, which Splunk truncated at 10,000 events), T1550.002 (mimikatz launched interactively, no `sekurlsa::pth` on the command line) and T1560.001 (Cobalt Strike 7z) are `recorded`. T1558.003 has no anchor and is `whole-file-head`: it is not an execution window and is a weak placeholder entry. T1218.005 is named in the description but recorded through AtomicTestHarnesses, so its command line is the harness variant of the VBScript test.
- **Baseline.** Splunk attack_data has no benign-only dataset (top-level folders checked at the pinned commit). `baseline.jsonl.gz` is therefore the lead-in of the recordings: per recording, the busiest host's events from the start to 30 s before the first Atomic-harness or attack-tool event, de-duplicated by event shape across recordings and thinned deterministically to 3,000 events. It is idle Windows Server 2016 domain-controller lab activity (boot, services, Splunk forwarder, harness PowerShell compiling helper assemblies), not a user workstation. The build refuses to emit a baseline event that matches any technique anchor.
- **Reproducibility and integrity.** `python -I backend/scripts/build_datasets.py --sources <dir> --check` rebuilds and compares against the committed files by uncompressed content hash (independent of the zlib build). `python -m purplebench catalog --check` (CI) validates the committed files against `manifest.json`: file sha256 and size, event counts per channel/event id, content hash, timestamp order, orphan files, licence files present, size budget, and library-to-manifest consistency (GUIDs, link labels, 20-30 techniques, at least 8 tactics).
- **Size.** 26 test files plus baseline are about 3.5 MB gzip (budget 30 MB).
- **Parse accounting.** The XML reader counts every event it cannot use, by reason (text outside an event, event too large, unterminated event, unparseable XML or DTD, missing System/TimeCreated, bad timestamp). The build prints the counts per source file and records them in `manifest.json` under `source.parse`. At the pinned commit all 26 source files parse with 0 skipped events.
- **Upstream NOTICE (Apache-2.0 section 4(d)).** Checked 2026-11-10: the full git tree of splunk/attack_data at `c8af10d015d392fca97f9eb65181e9f06bc18e40` (5,658 entries, not truncated) contains no `NOTICE` file, so there is no upstream notice text to carry. `backend/data/telemetry/NOTICE.md` is PurpleBench's own modification notice.
- **Library format.** `backend/data/library.json` holds technique metadata and, for each Atomic test, name, GUID, executor, command and cleanup text, input-argument defaults and source URL. `library.py` loads it; `command_resolved` substitutes defaults for display. Nothing executes the text. The per-technique `note` strings that explain a deviation are written by the generator (`SPECS`) and shown in the UI, so they are phrased for readers, not for the build.

## The Sigma evaluator

- **Own evaluator, documented subset.** `backend/purplebench/sigma/` (parser, mapping, evaluator) implements the subset in `docs/SIGMA_SUPPORT.md` against Sigma specification 2.1.0. Anything else loads with status `unsupported` and the exact reason; nothing outside the subset is evaluated as "no match". There is no pySigma dependency: it converts rules to backend queries rather than matching events.
- **Semantics chosen where the specification leaves room.** `null` matches an absent or empty field (Windows Event XML cannot tell them apart); `|re` is an unanchored search, case-sensitive unless `|re|i`; `windash` makes every `-`, `/`, en dash, em dash and horizontal bar interchangeable (the specification's wording; pySigma rewrites only word-initial dashes); keyword (full-text) search identifiers are unsupported (normalised events keep no raw message to search).
- **Regex guard.** `|re` runs on the `regex` module with a 50 ms time limit per match; a timed-out match counts as no match for that event, is counted in `RuleResult.regex_timeouts` and the detail, and is logged. The fifth timeout within one evaluation abandons the rule (`unsupported`, "regex too slow: |re timed out 5 times; rule abandoned"; `REGEX_MAX_TIMEOUTS_PER_RULE`), so the regex time of a rule is bounded at about 0.25 s regardless of event count. `evaluate_all` checks the profile type once and raises `TypeError` instead of reporting it per rule. A cheap static check stays as the first line (at most 1,024 characters, no backreferences, no unbounded repetition of a group that contains a quantifier or alternation, must compile); a rejected pattern makes the rule `unsupported` with the reason. `|re` sees at most the first 32,768 characters of a value.
- **Wildcards without regular expressions.** Plain values with `*`/`?` (and `windash`) are matched by a linear glob matcher (segments between `*` found leftmost-first with `str.find`), not compiled to `.*` regexes, so a value such as `*a*b*c*d` on a 30,000-character field cannot backtrack. A randomised test checks it against a regex construction. A glob lowercases with `str.lower()`, so the few characters whose lowercase is longer (for example U+0130) are a negligible known edge. `\*` is a literal star, as in Sigma 2.1.0.
- **Malformed rules never raise.** Logsource values must be strings; conditions may nest at most 64 levels (parentheses and `not`); regex compile errors, overflow, recursion and any other exception while parsing turn the rule into `unsupported` (`rule could not be parsed: <ExceptionType>`); `evaluate_all` reports a rule that fails at evaluation time as `unsupported` (`rule could not be evaluated: <ExceptionType>`) and carries on.
- **Telemetry gap vs no match.** Each rule source (channel + event ids + field map) is checked against a telemetry profile (channels, event ids and EventData field names that occur). Absent channel or event id, or fields whose absence makes the condition false under three-valued evaluation, make that source a gap; a rule with no evaluable source is `telemetry_gap` with the missing channel/fields in the detail. A field missing only in an OR branch or under `not` does not make a gap. The profile is a required argument of `evaluate`/`evaluate_all` (no silent per-window default); scoring passes the corpus profile (`recorded_profile()`) so a window that merely lacks an event id is judged against what the mode can record. `EventID` and `Channel` tests are decided literally per candidate (channel, event id): candidates the condition rules out are skipped (no noise gaps for other event ids), and a rule whose event ids never occur (for example kerberoasting on 4769 when only 4768 is recorded) is a `telemetry_gap` ("no Security event 4769 in the telemetry").
- **Security 4688 mapping.** `process_creation` reads Sysmon 1 and Security 4688; 4688 is mapped explicitly (`Image`<-`NewProcessName`, `ParentImage`<-`ParentProcessName`, `User`<-`SubjectDomainName\SubjectUserName`, hex process ids to decimal, `MandatoryLabel` SID to integrity name). Unit-tested; recorded mode has no Security channel, lab mode will.
- **Registry categories.** `registry_add` and `registry_delete` both map to Sysmon event 12 without checking `EventType`, so they are not told apart. No bundled rule uses either, so no result is affected; `docs/SIGMA_SUPPORT.md` states it.
- **ATT&CK tags.** Rule `attack.tNNNN` tags become technique ids through `library.technique_aliases()` (the library's dataset-id aliases, e.g. `T1562.001`->`T1685`, `T1070.001`->`T1685.005`). The pinned SigmaHQ release already uses v19+ ids in some rules (for example `attack.t1685.005`), which pass through unchanged. Tags for techniques outside the library are kept as they are.
- **SigmaHQ rule set.** 58 rules from https://github.com/SigmaHQ/sigma release `r2026-07-01`, commit `552f3fee420ef232a8e5790c4fae591847e32347` (tag object `19aee0af973becc96465791d9401272ca2841bf1`), fetched by raw URL and copied byte for byte into `backend/rules/sigmahq/` (upstream path, URL and sha256 per file in `SOURCES.json`; DRL 1.1 text in `LICENSE.Detection.Rules.md`; `.gitattributes` keeps the bytes free of EOL conversion). Chosen from the 2,403 Windows rules by relevance to the 26 techniques, to give a realistic mix: rules that fire on the recordings, rules that miss them, Security/System/PowerShell rules that are telemetry gaps in recorded mode, and four rules outside the subset (`base64offset` x3, `cidr`) so the unsupported path is exercised with real content. Upstream rules carry no `license:` field; their `author`, `id` and other fields are untouched.
- **Custom rules.** 12 rules in `backend/rules/custom/` by Andrew T. Price II, each closing a gap the bundled SigmaHQ set leaves on the recorded telemetry (for example the Sysmon `\(Default)` suffix that defeats SigmaHQ's eventvwr key match, `net localgroup` without a named group, process-creation versions of cmdlet rules that SigmaHQ only has for script block logging, and a harness-tuned encoded-command rule). Licence: **DRL 1.1**, the same as the SigmaHQ rules, so the rule folders carry one licence and anyone reusing the rules keeps the author attribution. Recorded in each rule's `license: DRL-1.1`. The rules were written against these same recordings, so the v4 coverage is a best case on known telemetry (see Scoring).
- **Rule-set versions.** `load_rules(directory, include=[...])` selects rules by id or file stem, so rule-set versions v1-v4 are lists.
- **Known limits of the recorded data for rules.** T1558.003 has no execution in its dataset (no rule can be credited); T1550.002 shows only an interactive tool accessing LSASS (credited to T1003.001 rules, not pass-the-hash); `proc_creation_win_powershell_encode` and `proc_access_win_lsass_memdump` also fire on the benign baseline (noisy).

## Scoring, coverage and gaps

- **Technique credit.** Rule tags are mapped to v20 ids by the alias table. A non-noisy rule tagged with exactly the tested id gives `detected`. `partial` otherwise, with the reason: "parent-technique rule" (only the parent of a tested sub-technique, e.g. T1569 for T1569.002), "detected via related technique <id>" (non-noisy rules for other techniques, including a more specific sub-technique of a tested parent), or "noisy rule" (only rules over the noise threshold fired, with their baseline hit counts). `missed` means no rule earned credit; `telemetry_gap` means nothing fired and every evaluable rule tagged for the technique is a telemetry gap against the whole recorded profile. T1558.003 is `untested` ("recorded dataset contains no execution") and excluded from every denominator.
- **Noisy credit is narrow.** A noisy rule counts toward `partial` only when it is tagged with the exact technique or its parent. A noisy rule tagged only for another technique earns nothing: the execution scores `missed` and the reason names the noisy rule, so the hit stays visible without implying the technique was partly detected. This keeps the status definition in the README and the code identical, and it keeps harness noise (for example the encoded-PowerShell rule matching the Atomic harness's own commands) from lifting the "partial as half" figure.
- **Time window and TTD.** Execution start is the manifest's first anchor event, not the window start. A match counts only in [start - 5 s, start + 120 s]; TTD is the first such match minus the start, clamped at 0, so skew gives 0 and lead-in or late matches neither earn credit nor distort TTD. Skew, window and noise threshold (default 0 baseline hits) are parameters of `score_run`. In recorded mode TTD is about 0 s because the anchor is the command's own process-creation event, which process-creation rules match directly; it is not SIEM detection latency.
- **Scores.** Overall and per-tactic score = detected / tested; techniques are best-of their executions; multi-tactic techniques count in each tactic and once overall. `partial_score` (partial at half weight) is reported separately. The weighting is a display choice and is never mixed into the detected score.
- **Best case.** The 12 custom rules were written against the same recordings the demo scores them on, so the v4 result (22 of 25, 88%) is a best case on known telemetry, not a generalisation. The README, UI and reports say so.
- **Navigator.** Layer 4.5 (`navigator` 5.3.2, ATT&CK 20); detected 100 / partial 50 / missed and gap 0; untested has no score. `tactic` is omitted so multi-tactic techniques show in all their tactics. `validate_layer` implements the documented required and optional fields used. The default description says the telemetry is mostly Atomic Red Team tests (not all recordings are Atomic runs) and carries the ATT&CK notice.
- **Gap hints.** `backend/data/gap_hints.yml`, keyed by v20 id, "telemetry needed" and "rule idea" for each of the 26 techniques; a test requires full coverage of the library. Hints are starting points, not tested rules. A gap is created for every missed, partial or telemetry-gap execution (the single definition, used by the demo builder and the importer).

## Storage, authentication and the demo

- **Auth and config** follow the pattern of the sibling apps CMMC Ready and STIGWatch (`PURPLEBENCH_` prefix, cookie `purplebench_session`, PBKDF2 600k hashing, signed httpOnly SameSite=Strict cookie, per-IP login limiter, fail closed, read-only guests in demo mode). `python -m purplebench create-admin` exists because the 503 message points to it.
- **Blank environment values mean unset.** `backend/.env.example` is meant to be copied, so a line such as `PURPLEBENCH_DB=` must not break the app. Every getter in `config.py` reads `os.environ.get(NAME) or default`, a malformed number falls back to the default, and optional lines in `.env.example` are commented out. A test loads `.env.example` verbatim, opens the database, logs in and serves `/api/health`.
- **Schema.** Tables for campaigns, rule sets, runs, executions, hits, gaps and rule noise, plus `ruleset_rules` (which rule ids each version enables, with the version that first enabled the rule and a remark), `rule_noise` (every rule's hit count on the benign baseline per run), `hits.relation/noisy/noise_hits/record_ids_json` (matched event record ids; the API pages events from the file named in `executions.events_ref`), `executions.reason`, and `gaps.telemetry_needed/rule_idea/closed_in_run`. A gap `kind` is `missed`, `telemetry_gap` or `partial`. Rule YAML stays in the repository; `rulesets.rules_json_hash` is a SHA-256 of rule id, file name and line-ending-normalised content, and a test recomputes it against the files.
- **Migrations.** `db.connect` migrates older databases in place (PRAGMA user_version): version 2 widened `executions.status` (`did_not_run`; the table is rebuilt, rows, hits and cascades preserved), version 3 widened `gaps.status` (`accepted`), version 4 added `gaps.analyst_notes`. A lab run imported by an earlier build carried a project-level sentence about the lab runner in its stored source; connecting strips it, because that statement is not run data.
- **Gap notes.** Importer text stays in `gaps.notes` (API `system_notes`); PATCH writes `gaps.analyst_notes` (API `notes`); API `display_notes` joins both.
- **Everything is computed at build time.** `backend/scripts/build_demo.py` runs the real `score_run` (profile `recorded_profile()`, noise threshold 0) for each run and writes `backend/data/demo_fixture.json`; `--check` rebuilds and compares (also a CI step and a test). A cold start only loads the fixture. Execution timestamps are the original recording's; run and rule-set dates are relative to the fixed anchor 2026-09-28.
- **Seeding** is atomic (`BEGIN IMMEDIATE`, re-check inside the lock, rollback on any error; runs are inserted before their executions and gaps so a gap can refer to the run that closed it). A seeding failure is logged once and cached for 60 s; data routes answer 503 "Demo data is not available yet" meanwhile, so a broken database is not re-seeded on every request.
- **Campaigns.** "Initial access to credential theft" (15 techniques including the untested T1558.003) and "Ransomware precursors" (14); T1059.001, T1003.001 and T1053.005 are in both.
- **Run schedule (6 weeks).** Run 1: credential theft + v1 (day 0). Run 2: ransomware + v2 (day 14). Run 3: credential theft + v3 (day 28). Run 4: ransomware + v4 (day 42). Each campaign is run twice, so a gap closes or stays open between its two runs; the progression table in the fixture (`meta.progression`) also scores every version over every campaign for context, but only the four runs are stored.
- **Rule set narrative** (cumulative; the per-rule remark is stored with the rule set):
  - **v1 (15 SigmaHQ rules)**: the starter set (ProcDump LSASS, shadow copy deletion x2, log clearing, Run key, schtasks, `net user /add`, certutil download, regsvr32, mshta child processes, PsExec, `proc_access_win_lsass_memdump`, and three Security/System rules). Credential theft campaign: 6 of 14 detected (42.9%); T1550.002 reads as a telemetry gap (the Security-channel pass-the-hash rule cannot see anything in recorded telemetry). `proc_access_win_lsass_memdump` is already noisy (2 baseline hits) but T1003.001 is detected by the ProcDump rule anyway.
  - **v2 (+15 SigmaHQ)**: services, WMI, Defender tampering, `net view`, `wmic` group recon, the Event Viewer UAC bypass rules, mshta JavaScript, plus the popular encoded-PowerShell rule (`proc_creation_win_powershell_encode`, 5 baseline hits). Ransomware campaign: 9 of 14 detected (64.3%, 75.0% counting partial as half). For T1059.001 the noisy rule's exact credit is withheld and only a related mshta JavaScript hit (T1218.005) remains, so it is partial. T1082 is missed: the only rule that fired is the noisy encoded-PowerShell rule, which is tagged for T1059.001, so it earns nothing. The two Event Viewer UAC rules do not match the recording (Sysmon writes `...\command\(Default)`), and `wmic_recon_group` never matches the recorded `net localgroup` and is itself noisy (1 baseline hit): T1548.002 and T1069.001 stay open.
  - **v3 (+4 custom)**: each closes a gap seen in runs 1 or 2. `powershell_encoded_command_tuned` replaces the noisy rule as the credit source for T1059.001 (missed in run 1, partial in run 2 with the noisy rule's credit withheld) and T1027; the SigmaHQ rule stays enabled and visibly noisy. `net_localgroup_enumeration` closes T1069.001, `7zip_split_or_max_compression` T1560.001 (SigmaHQ's 7-Zip rule covers only password-protected archives), `quser_qwinsta_session_discovery` T1033. Credential theft campaign: 10 of 14 (71.4%), up 28.5 points from run 1.
  - **v4 (+36, the full 70)**: the held-back UAC rules (custom `registry_set_uac_bypass_shell_open_command`, which handles the `\(Default)` suffix, and SigmaHQ fodhelper/UAC-disable), `rundll32_mshtml_script_protocol` (the comparable SigmaHQ rule has no ATT&CK tag) for T1218.011, `reg_dumping_sensitive_hives`/`esentutl` for T1003.002, `systeminfo_execution` for T1082, and the remaining second rules and out-of-telemetry rules. Ransomware campaign: 12 of 14 (85.7%). Over all 25 tested techniques the versions score 36%, 52%, 72%, 88%.
- **Gaps and closure.** One gap per missed, telemetry-gap or partial execution. In the demo, a gap is `closed` when the later run of the same campaign detects the technique (the note names the rules that credit it). Only the demo builder closes gaps automatically: importing a lab run opens gaps for that run but does not close earlier open gaps of the same campaign, because lab and recorded runs differ in telemetry and a later detection on different data is not obviously the same gap. Admins can accept or re-open a gap by hand. Gaps that stay open say so: T1569.002 and T1021.002 stay partial (no bundled rule is tagged with the exact sub-technique), T1550.002 stays a telemetry gap (the recording has no Security channel and no `sekurlsa::pth` command line). Gaps still open in run 3 that rule set v4 would close (T1548.002, T1218.011, T1003.002) are labelled "Not re-run yet" rather than counted as closed, because the credential theft campaign has no v4 run.
- **Honesty.** Every demo run carries `mode = recorded` and a source string naming Splunk attack_data and stating that nothing was executed. Unsupported rules (`|base64offset`, `|cidr`) and telemetry-gap rules stay in the rule sets and are reported as such.

## API

- **Body limits are path-aware:** 64 KiB for every POST/PUT/PATCH except `POST /api/runs` (upload cap + multipart allowance). The check uses `Content-Length` first and also counts bytes as they arrive.
- **Empty database.** `rulesets.ensure_bundled_ruleset()` creates a rule set `bundled` (every bundled rule) on first `POST /api/runs` when none exists (demo and non-demo); idempotent.
- **API docs** (/docs, /redoc, /openapi.json) are off; the schema is at `/api/openapi.json`, writers only.
- **Rule objects** carry `licence: "DRL-1.1"` (custom rules are derived from SigmaHQ rules). `load_all_rules` is cached per rule-file set, keyed by file modification times.
- **Dashboard data.** Execution events accept `matched=true` and `rule=<id>` (server-side, before paging); run detail lists each execution's fired rules (id, title, author, relation, noisy). `GET /api/rules/{id}` returns `hits_total` and `hits_capped`. `GET /api/campaigns/{id}` returns `download_filename`, the single definition also used for the export's Content-Disposition. Hit keys `[null, n]` and non-object event lines are tolerated (skipped and counted in `events.skipped_lines`).
- **Event paging.** An event is validated (parsed, object, usable time, renderable) before any paging decision, so a malformed line is skipped and counted the same way on every page; pages never repeat or lose an event. `json.loads` recursion errors are skipped and counted too.
- **`skipped_lines` and `total` are lower bounds** unless a filter (`matched` or `rule`) is used: without a filter the scan stops after the page and one more event, so only the lines scanned so far are counted (`total_is_lower_bound`), because counting every line of a large lab file on each page request would be costly. With a filter the whole file is scanned and `total` (distinct events passing the filter; an event matched by several rules counts once) is exact, and `skipped_lines` counts the unusable lines that pass the filter.
- **Database open failure** returns 503 "The database is not available" instead of a 500, including the connection opened after a cold-start seeding.
- **Frontend pager and writes.** The matched-events pager uses the server's `total` and `total_is_lower_bound` (an old response without them falls back to the selected rule's count; per-rule counts are never summed), shows "Matches a-b of N" or "of at least N", and bounds Next by the exact total with `has_more` as the fallback. Failed writes show friendly text for 503 and network errors rather than the raw message.

## Lab runner and run import

- **Runner** (`lab/Invoke-PurpleBenchRun.ps1`, PowerShell 5.1 and 7). Order of guards: parameter validation, allow-list (exact name, local, before any network traffic), campaign validation, `-WhatIf` (prints the plan; contacts nothing, writes nothing), then one WinRM session to the named target, the on-target marker `HKLM:\SOFTWARE\PurpleBench\LabTarget = 1` (DWORD only; a string "1" is refused), a check that the host answers to the name given and that Invoke-AtomicRedTeam is already installed, then the warning and a typed, case-sensitive target name, then the tests. The marker read happens before the prompt so the operator is never asked to confirm something that would be refused. Campaign values are regex-validated and passed to the remote side as arguments, never spliced into code. Start and end times are taken from the target's clock (the events carry that clock). Events with strings over the limits are dropped by the runner and counted (`dropped_oversize`), never truncated, because partial evidence could mislead; the importer likewise skips and counts any over-limit event and keeps the rest of the file, and an execution whose every event was left out is imported as `did_not_run` ("all collected events exceeded size limits"), not as missed. The runner drops events with XML over 60,000 characters. Collection is capped per log (`-MaxEventsPerTest`) with a warning. The run file is written (never overwriting) in a `finally`, so a run that aborts keeps the completed tests. Modules for the remote session are installed for all users on the target (documented) instead of adding a module-path parameter. Defaults: settle 120 s, 10 s pause after cleanup, Credential mandatory for real runs, refusals exit 1, run file created with CreateNew. Technique and GUID patterns are ASCII-only in both languages.
- **Run file (version 2).** Events travel as `Event.ToXml()` and are normalised only by `telemetry.parse_event_xml`; each execution carries `run_status` (ran, failed, prereqs_missing, skipped), `error`, `collection_error` and `truncated`. Lab hits store `[channel, record_id]` pairs (record ids repeat across logs).
- **`did_not_run`.** A status for tests that did not run or whose collection failed. It is part of the schema CHECK, `scoring.STATUSES`, coverage, the Navigator legend and the run summary, is excluded from coverage denominators like `untested`, and is never scored as missed.
- **Campaign file format** the runner reads (the `export.json` route produces it): `{"format":"purplebench-campaign","version":1,"name":...,"tests":[{"technique_id","test_guid"}]}`.
- **Import** (`runfile.py`): strict validation, then scoring with the newest rule set (or a chosen id) by the same `score_run`. A lab run has no benign baseline, so rule noise is not measured (stated in the run notes), and the telemetry profile is built from the run's own events. The execution window is 120 s plus the test duration. Events are stored as gzip JSON lines in `lab_events/` next to the database (`events_ref` = `lab_events/run<id>_<n>.jsonl.gz`); the API pages them from there. Import is one transaction; event files are removed on failure; `import_run` refuses a connection with an open transaction rather than committing it. Unknown technique ids import with the id as the name.
- **The "not yet run against a real lab" statement is project-level.** It lives in the README, `lab/README.md`, the UI (Campaigns page lab panel, mode notice), the reports and `MODE_NOTES`, and it is not stored on imported runs, because it stops being true when the runner is first used on a real lab and stored text would go stale.
- **Tests.** Static text tests (`test_lab_runner_static.py`) plus `lab/Test-RunnerStatic.ps1` (PowerShell AST) in a `windows-latest` CI job on both PowerShell editions. Pester is deliberately not used: parameter-validation tests would execute the runner, which must not run anywhere until a lab exists; a manual check is documented in `lab/README.md`.
- **Sysmon config** suggested in the README: olafhartong/sysmon-modular (MIT, verified through the GitHub API). SwiftOnSecurity/sysmon-config is mentioned with the caveat that GitHub shows no machine-readable licence.
- **Status.** Lab mode has not yet been run against a real lab.

## The lab runner's static check

`lab/Test-RunnerStatic.ps1` parses the runner with `[System.Management.Automation.Language.Parser]::ParseFile` and requires everything to be on an explicit allow-list. A deny-list is always incomplete (Start-Process aliases, native `powershell -enc`, LOLBins, aliases, `InvokeScript`, `Assembly::Load`, `& script.ps1`, dot-sourcing, `Invoke-Command -FilePath`, path imports, Defender policy keys, Stop-Service and firewall changes all have to be caught), so the old deny-list is kept only for clearer messages. It runs in a CI job on `windows-latest` under Windows PowerShell 5.1 and PowerShell 7.

- **Commands (local):** Set-StrictMode, Test-Path, Split-Path, Join-Path, Get-Content, ConvertFrom-Json, ConvertTo-Json, Get-Date, Get-Location, Write-Host, Write-Warning, Read-Host, Start-Sleep, Where-Object, Select-Object, New-Object, New-PSSession, Invoke-Command, Remove-PSSession, and the runner's own Stop-Refused, Test-AllowListed, ConvertTo-IsoUtc, Get-RoundtripDate (no other function may be defined).
- **Commands (inside script blocks sent to the target; tighter):** Get-ItemProperty, Get-WinEvent, Get-Module, Import-Module, Invoke-AtomicTest, Out-String, ForEach-Object, New-Object. Remote blocks are found through `Invoke-Command -ScriptBlock $var` (the variable must be assigned once from a `{ }` literal). `Invoke-AtomicTest` may use only -TestGuids, -PathToAtomicsFolder, -CheckPrereqs, -Cleanup, -Confirm, -ErrorAction, -ErrorVariable (never -GetPrereqs, which downloads); `Import-Module` only `-Name 'Invoke-AtomicRedTeam'` (a module name, never a path).
- **Rules for every command:** a literal bare-word name (computed names, quoted names, `&` and dot-sourcing fail); aliases and native executables fail because they are not listed (powershell/pwsh/cmd, paths, `.exe`); any `-EncodedCommand` abbreviation (-e, -ec, -enc, ...) fails on every command; `Invoke-Command` takes only -Session, -ScriptBlock and -ArgumentList in full spelling (no -FilePath, no -ComputerName); `New-Object` only for System.Collections.Generic.List[string], System.Collections.Generic.List[object], System.Text.UTF8Encoding, System.IO.FileStream. `New-PSSession` only as `New-PSSession @sessionArgs`, with `$sessionArgs` holding `ComputerName = $Target`.
- **.NET:** static members only `DateTime::Parse`, `DateTime::UtcNow`, `string::IsNullOrWhiteSpace`, `CultureInfo::InvariantCulture`, `DateTimeStyles::RoundtripKind`, `FileMode::CreateNew`, `FileAccess::Write`, `FileShare::None`; instance calls only ToString, ToXml, GetUnresolvedProviderPathFromPSPath, Add, ToArray, Dispose, Write, ToLowerInvariant, ShouldProcess, Substring, ToUniversalTime, ToLocalTime, Trim, AddSeconds, GetBytes; member names such as InvokeScript, InvokeCommand, ExpandString, Load, LoadFrom, LoadFile, Download*, Upload*, OpenRead, Create, Invoke fail everywhere; dynamic member names fail; `$ExecutionContext` only in `$ExecutionContext.SessionState.Path.GetUnresolvedProviderPathFromPSPath(...)`. Also failing: `using` statements, redirection to a file, Set-Alias/New-Alias/sal/nal.
- **Gates, structurally (not by word search):** `if (-not (Test-AllowListed -Name $Target ...)) { Stop-Refused }` before `New-PSSession`, and Test-AllowListed compares with `-eq` only; `-WhatIf` branch (`if ($WhatIfPreference)`) that ends with `return`, needs no credential, opens no session, prompts for nothing, and comes before the credential check; `if (-not $Credential) { Stop-Refused }` after it and before `New-PSSession`; the first remote call is the marker block, which reads `HKLM:\SOFTWARE\PurpleBench` `LabTarget`, followed by `if (($info.Marker -isnot [int]) -or ($info.Marker -ne 1)) { Stop-Refused }`; the one `Read-Host` answer compared with `-cne $Target` in an if that calls Stop-Refused, after the marker gate and **before every state-changing remote call** (the run, cleanup and collect blocks); Stop-Refused ends in `exit 1`; Target and Campaign mandatory; Credential a PSCredential. The typed confirmation cannot come before `New-PSSession`, because the marker check (a read-only remote call) must happen first so that the confirmation can name a verified lab VM; the rule enforced is confirmation before any remote call that changes anything. `-Credential` is a refusal for real runs rather than `Mandatory = $true`, because `-WhatIf` must work without one.
- **Gate integrity.** The checker also protects the runner's structure against edits. (1) Every function name may be defined once and only at the top level of the script (a second `function Stop-Refused {}` or one inside an `if` fails), and any write to the `function:` drive, or to any drive-qualified variable such as `env:`, fails (`Set-Item` is not allowed anyway). (2) Protected variables: every parameter of the runner (Target, Campaign, Credential, AtomicsPath, ... with OutFile defaulted at most twice and LabTargetsFile once, as the runner does), `$sessionArgs` (1 assignment, plus `.UseSSL = $true`), `$session` (2: `$null`, then `New-PSSession @sessionArgs`), `$info`, `$typed`, `$tests`, `$camp`, `$campaignName`, `$tech`, `$guid`, `$markerBlock`, `$utcNowBlock`, `$runBlock`, `$cleanupBlock`, `$collectBlock`, `$TechniquePattern`, `$GuidPattern`, `$MaxTests`, `$ErrorActionPreference` (1 each), and the automatic or preference variables WhatIfPreference, ConfirmPreference, PSDefaultParameterValues, ExecutionContext, PSCmdlet, MyInvocation, PSBoundParameters, PSScriptRoot, ErrorView, PSModuleAutoLoadingPreference (0). A write is any assignment (`=`, `+=`, multi-assign, typed, `$script:`/`$global:` scoped, member or index targets such as `$sessionArgs['ComputerName']`), `++`/`--`, a foreach loop variable, `[ref]`, a `-ErrorVariable`/`-OutVariable`/`-WarningVariable`/`-InformationVariable`/`-PipelineVariable` (and their short forms) naming one, a method call on `$sessionArgs`, and Set/New/Clear/Remove-Variable (not on the allow-list). Anything past the permitted initialisation fails. (3) Splatting fails everywhere except `New-PSSession @sessionArgs`, and `$sessionArgs` must be one literal hashtable with only `ComputerName = $Target`, `Credential = $Credential`, `ErrorAction = 'Stop'`. (4) Writes to `env:` (local or inside a remote block, for example `$env:PSModulePath`) and to `$PSDefaultParameterValues` fail. (5) A gate must be the first clause of an if statement whose condition is exactly the expected text (so `-and $false` fails), whose body begins with a direct `Stop-Refused` call, and which is not nested in an if, loop, switch, function, catch or script block (so a dead branch fails); the `-WhatIf` branch must end with a top-level `return`.
- **References and pinning.** `$sessionArgs` may appear only in its one literal-hashtable initialisation, in `.UseSSL = $true`, and as `New-PSSession @sessionArgs`; any other reference (`$h = $sessionArgs`, a read, a string expansion, a method call) fails, because an alias would let `$h.ComputerName = ...` retarget the session after the allow-list gate. `$info` (the marker answer, read by the marker gate) may only be assigned once and read as `$info.Property`. Every member or index write (`$x.Prop = ...`, `$x['k'] = ...`, `$x.Prop++`) fails except on `$exec`, the runner's own result record (and `$sessionArgs.UseSSL = $true`), so an alias cannot be used to change `$tests`, `$camp` or another object after validation. `Stop-Refused` and `Test-AllowListed` are pinned: the checker holds their text (whitespace collapsed) and fails on any difference, with a message that the pinned text must be updated deliberately, in the same commit, alongside the function.
- **`$exec` is restricted too.** Because `$exec` carries the technique and GUID that reach `Invoke-AtomicTest`, the only permitted whole-variable assignment is its single `[ordered]@{ ... }` literal; member writes (`$exec.Prop = ...`) stay allowed. Any other assignment (`$exec = $tests[1]`), use as a `foreach` or `for` loop variable, or naming it in `-OutVariable`/`-ErrorVariable` and the other `-*Variable` parameters fails, so an alias cannot make `$exec` point at validated data and then be edited through a member write.
- **Deliberately not restricted (reviewed, not exploitable).** `$session` (opened after the gates; an alias cannot change where it points), `$Credential` (an immutable PSCredential), `$tests`/`$camp` (JSON data; changing their contents needs a member or index write, which is forbidden), `$executions`/`$problems` (output lists). A string cast to a script block does not convert it, and `-ArgumentList` strings are passed as data and never evaluated; assigning `$env:PATH` or other variables that cmdlets do not consult cannot change which cmdlet runs (the checker still rejects every `env:` write); a try/catch or trap around a gate cannot swallow `exit`, and an early `exit 0`, `Set-StrictMode`, or a second `UseSSL = $true` only stop or tighten the run. There is no protection against someone who rewrites the runner and the checker together, which is what reading the script before running it is for.
- **Self-test (`lab/Test-RunnerStatic.SelfTest.ps1`).** The unchanged runner must pass; appended lines, changes inside the remote script blocks, weakened or removed gates and `$exec` alias cases (parsed in memory with `-ScriptText`) must each fail with the expected message; and `lab/selftest/forbidden-command.fixture.ps1` (a benign `Get-Date` through the forbidden dynamic-evaluation cmdlet; parsed, never run) must fail from disk. Nothing that looks like an attack command line is written to disk (Defender quarantines those): risky words are split with a marker removed at run time. A pytest test runs the self-test when PowerShell is present.
- **A static check is defence in depth, not a sandbox.** It cannot prove what a script does at run time; the operator is still expected to read the runner before using it, and the runner's own gates (allow-list, marker, typed confirmation, credential) are what protect the lab.

## Deployment, documentation and CI

Verified 2026-11-10.

- **Vercel limits (verified).** https://vercel.com/docs/functions/limitations: Python functions may be 500 MB uncompressed (250 MB for other runtimes), request and response bodies 4.5 MB (`413 FUNCTION_PAYLOAD_TOO_LARGE`), Hobby max duration 300 s. https://vercel.com/docs/functions/runtimes/python: standard Python bundle limit 500 MB; files are included by `includeFiles`/`excludeFiles` globs relative to the project root. `vercel.json` sets `maxDuration` 30 and `includeFiles` to `backend/purplebench/**`, `backend/data/**` and `backend/rules/**`.
- **Bundle measured, nothing trimmed.** `pip install -r requirements.txt --target` of the root requirements (fastapi, pyyaml, python-multipart, pyjwt, defusedxml, regex) is 19.4 MB on Windows (Linux wheels are of similar size); the application files (package, data, rules) are 4.2 MB, of which the 26 trimmed telemetry files plus baseline are 3.5 MB. Total about 24 MB against 500 MB, so the telemetry was not trimmed. A test fails if the application files grow past 20 MB so the budget is revisited on purpose. The root `requirements.txt` is the Vercel function's list (no uvicorn, no test tools).
- **Request body limit on Vercel (4.5 MB).** The app's demo upload cap is 4 MB, plus 64 KiB multipart overhead, which is under 4.5 MB. `config.max_upload_bytes()` additionally clamps the cap to 4 MB when the `VERCEL` environment variable is set, whatever `PURPLEBENCH_MAX_UPLOAD_MB` says, so the app answers with its own 413 JSON instead of Vercel's platform error for any file the platform would accept. `/api/health` reports the effective `max_upload_mb`. A platform refusal is not the app's JSON (it can be a non-JSON 413 or look like a network failure), so the upload form checks the size before sending, and its error text for a 413 without the app's wording, and for a network failure, says the platform may have cut the file off.
- **Entry point.** `api/index.py` sets `PURPLEBENCH_DB=/tmp/purplebench.db`, demo mode, trusted proxy and the 4 MB cap with `setdefault`, then imports the app. It does not seed at import: the app seeds lazily at startup or on the first data request and answers 503 "Demo data is not available yet" while that fails (cached for 60 s), so a broken `/tmp` cannot stop the function from loading. Tests import `api/index.py`, serve a data route, check the 503, and check `BodyLimitMiddleware` behind the rewrite: FastAPI sees the original `/api/...` path, so only `POST /api/runs` (and `/api/runs/`) keeps the upload cap and every other body stays at 64 KiB.
- **Admin writes on the hosted demo are deliberate.** Only the owner holds the password (a login exists only if the owner sets `PURPLEBENCH_ADMIN_PASSWORD_HASH` and `PURPLEBENCH_SECRET_KEY`; guests are read-only and nobody else can sign in), logins are rate-limited per client address (per serverless instance), and the `/tmp` database resets on a cold start, so a change by the owner is never permanent. While signed in on the demo (`session.demo && !session.guest`) a persistent notice beside the admin controls says: "Demo: changes you make are visible to other visitors until the demo resets."
- **Generated doc and `--check`s.** `python -m purplebench docs` writes `docs/COVERAGE.md` from the bundled rules and the demo fixture (rule inventory with unsupported reasons, coverage by rule-set version, latest run per campaign with each rule's author); `--check` fails when it is stale. `docs/SIGMA_SUPPORT.md` stays hand-written because it states the subset. `python -m purplebench demo --check` runs the fixture rebuild comparison (`backend/scripts/build_demo.py --check`); `demo --serve` loads the demo into its own database file (never the configured one) and serves it in demo mode; `serve` runs uvicorn.
- **CI.** Backend: pytest with `-rs` (any skip is named; the PowerShell-dependent tests run where `powershell` or `pwsh` is on the PATH, which includes the Ubuntu runner), `catalog --check`, `docs --check`, `demo --check`. Frontend: tests, build and `npm audit`. Audits cover both requirements files; gitleaks; the PowerShell job above. A separate **e2e** job runs the Playwright smoke test with the runner's preinstalled Chrome and is **non-blocking** (`continue-on-error`): it proves the browser path but a Chrome or runner change should not block a data or code fix. It has its own `e2e/package.json` (playwright 1.61.0, released 2026-06-15) so the app's `npm ci` and `npm audit` do not pull it in. The workflow layout follows STIGWatch's (backend, frontend, audit, secrets).
- **Node.** `package.json` `engines` is `^20.19.0 || >=22.12.0` (what Vite 8 needs); the README says "20.19+ or 22.12+". CI uses Node 22 LTS because Node 20 reached end of life in April 2026.
- **Screenshots** at 1400 px wide are written by `e2e/smoke.mjs --shots docs/screenshots` (tall pages cut at 2400 px).
- **README sources.** Cited only after fetching them on 2026-11-10: the Atomic Red Team repository description, and Picus Security's Blue Report 2025 press release (vendor data and promotional; the README says so). Nothing else is cited: MITRE's ATT&CK updates page confirmed the v20 release date (13 October 2026) but does not describe the v19 restructuring (that is cited from the April 2026 update page recorded above), and the CTID "Summiting the Pyramid" page said too little about testing to support a claim, so it was dropped.
